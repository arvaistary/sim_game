# Feature Specification: Сквозной аудит целостности проекта

**Feature Branch**: `003-project-integrity-audit`  
**Created**: 15 июля 2026  
**Status**: Completed
**Input**: Провести сквозной аудит связей Game Life, устранить ошибки и несостыковки логики, интерфейса, маршрутов, состояния и режимов исполнения; закрепить исправления регрессионными тестами и документацией.

## Цель

Получить проверяемую картину фактического состояния игры, устранить подтверждённые дефекты без архитектурных регрессий и зафиксировать результаты так, чтобы следующий аудит воспроизводился по тем же шагам.

## Clarifications

### Session 2026-07-15

- Q: Какой контракт поддержки режимов считать эталоном аудита? → A: SPA, Server и Hybrid обязаны иметь полную функциональную эквивалентность уже сейчас.
- Q: Какие findings обязательно исправлять в рамках 003-project-integrity-audit? → A: Исправлять все P0–P3 до завершения work item.
- Q: Что означает полная функциональная эквивалентность режимов? → A: Одинаковые допустимые действия, итоговое состояние и видимый результат; внутренний механизм может отличаться.
- Q: Что считать источником ожидаемого поведения при конфликте кода, тестов и документации? → A: Активная spec → constitution/ADR → актуальный GDD; код и тесты — фактическое поведение.
- Q: Какая viewport-матрица обязательна для каждого игрового маршрута? → A: 390×844, 768×1024, 1440×900.

## Рабочий промт аудита

```text
Ты — ведущий инженер по качеству Game Life. Работай только от проверяемых фактов из кода, тестов, запущенного приложения и актуальной архитектурной документации.

Цель: найти и устранить несостыковки между domain, application, infrastructure, Pinia stores, composables, компонентами, страницами, Nitro API и режимами SPA/Server/Hybrid.

Порядок работы:
1. Зафиксируй baseline: git status, структура модулей, маршруты, API endpoints, существующие тесты и команды проверки.
2. Запусти typecheck, ESLint, Stylelint, rules audit, Vitest и production build. Для каждого сбоя сохрани команду, вывод и затронутые файлы.
3. Проверь направленность импортов и разделение ответственности: domain не зависит от Vue/Nuxt/Pinia/browser API; application не содержит UI-логики; presentation не содержит новых доменных правил.
4. Проверь игровые сценарии end-to-end: старт персонажа, основной цикл, действия, время, финансы, карьера, образование, события, сохранение/синхронизация. Сверяй изменения GameWorld, UI projections и видимые результаты.
5. Проверь все реальные маршруты `src/pages/`, навигацию, loading/error/empty states, модальные окна, адаптивность и соответствие Nexus UI. Подтверждай UI-дефекты воспроизводимым сценарием.
6. Проверь контракт SPA/Server/Hybrid: executor selection, Nitro endpoints, сериализацию, обработку ошибок, offline queue, повторную синхронизацию и отсутствие server-to-client import нарушений.
7. Оформи findings с ID, severity (P0–P3), доказательством, причиной, затронутым слоем, шагами воспроизведения, ожидаемым и фактическим результатом, предложенным исправлением и регрессионной проверкой.
8. Не исправляй код до утверждённых `plan.md`, `tasks.md` и `/speckit.analyze`. После утверждения исправляй по одному связанному набору дефектов, добавляй или обновляй тесты, повторяй все релевантные проверки и синхронизируй документацию.
9. Не меняй архивные документы и не расширяй scope до Stage 8 server-first, платформенной дистрибуции или нового геймдизайна, если это не требуется для исправления подтверждённого дефекта.

Критерий завершения: каждый подтверждённый finding уровня P0–P3 устранён и покрыт регрессионной проверкой; blocked finding блокирует завершение до снятия внешнего условия или доказанного отклонения finding. Все обязательные quality gates проходят без необоснованных исключений.
```

## User Scenarios & Testing

### User Story 1 - Достоверный baseline и реестр дефектов (Priority: P1)

Как владелец проекта, я получаю воспроизводимый аудит состояния игры, чтобы видеть реальные дефекты и их приоритет до начала исправлений.

**Why this priority**: Без проверяемого baseline исправления будут случайными и могут скрыть более серьёзные нарушения.

**Independent Test**: Аудит можно выполнить на чистом рабочем дереве; каждый finding содержит команду или сценарий воспроизведения и доказательство.

**Acceptance Scenarios**:

1. **Given** исходный код проекта, **When** запускается аудит baseline, **Then** создаётся реестр результатов всех обязательных проверок и подтверждённых дефектов.
2. **Given** finding в реестре, **When** другой разработчик следует его шагам, **Then** он получает тот же наблюдаемый результат или явно отмеченную причину невоспроизводимости.

---

### User Story 2 - Целостная игровая логика и состояние (Priority: P2)

Как игрок, я выполняю основной игровой сценарий без рассинхронизации между правилами игры, состоянием и отображением UI.

**Why this priority**: Рассинхронизация состояния разрушает результаты действий и сохранения игрока.

**Independent Test**: Для каждого критического сценария есть проверка переходов состояния и видимого результата после действия.

**Acceptance Scenarios**:

1. **Given** созданный персонаж, **When** игрок выполняет действие, которое меняет время, деньги или шкалы, **Then** доменная модель, UI state и экран показывают согласованный результат.
2. **Given** выполнение в каждом поддерживаемом режиме, **When** сценарий завершается или синхронизируется после offline, **Then** состояние не теряется и не применяется дважды.

---

### User Story 3 - Согласованный интерфейс и маршруты (Priority: P3)

Как игрок, я открываю каждый доступный раздел игры и понимаю его состояние, ошибки и результат выполненного действия.

**Why this priority**: Недоступные маршруты, сломанная навигация и неотражённые ошибки блокируют доступ к уже реализованным механикам.

**Independent Test**: Матрица маршрутов и ключевых UI-сценариев проходит на поддерживаемых размерах экрана без console errors и тупиковых переходов.

**Acceptance Scenarios**:

1. **Given** пункт навигации или прямой URL, **When** игрок открывает игровой раздел, **Then** он видит соответствующую страницу и может вернуться в допустимый раздел.
2. **Given** пустое состояние, ошибка сети или недоступное действие, **When** UI отображает результат, **Then** игрок получает понятное состояние без повреждения игрового процесса.

---

### User Story 4 - Безопасное устранение подтверждённых дефектов (Priority: P4)

Как сопровождающий разработчик, я исправляю подтверждённые дефекты малыми проверяемыми наборами, не нарушая архитектурные правила и ранее работающие сценарии.

**Why this priority**: Исправление без регрессии важнее скорости закрытия отдельной ошибки.

**Independent Test**: Каждый закрытый finding связан с изменением, регрессионной проверкой и результатом quality gates.

**Acceptance Scenarios**:

1. **Given** утверждённый finding, **When** его исправление завершено, **Then** сценарий воспроизведения больше не показывает дефект и соответствующая регрессионная проверка проходит.
2. **Given** набор завершённых исправлений, **When** запускаются обязательные quality gates, **Then** нет новых нарушений архитектуры, типизации, стиля или тестов.

### Edge Cases

- Дефект проявляется только в SPA, Server или Hybrid режиме; finding обязан явно указывать проверенные и непроверенные режимы.
- Одинаковое действие приходит повторно после offline sync; аудит проверяет отсутствие двойного применения.
- Документация противоречит коду или содержит устаревший Phaser/ECS материал; это фиксируется как документационная несостыковка и исправляется в текущих docs/ADR/specs.
- Код или тест противоречит источнику ожидаемого поведения; finding оценивается по иерархии active spec → constitution/accepted ADR → актуальный GDD, а существующий тест не считается доказательством корректности сам по себе.
- Проверка требует отсутствующей среды, учётных данных или внешней сети; finding отмечается как blocked с нужным условием, а не объявляется исправленным.
- Предложенное исправление затрагивает несколько слоёв или публичный API; оно не реализуется до явного отражения риска и миграции в plan/tasks.

## Requirements

### Functional Requirements

- **FR-001**: Аудит MUST создать baseline по состоянию рабочей копии, структуре модулей, маршрутам, API, тестам и quality gates.
- **FR-002**: Аудит MUST проверить соблюдение слоистой архитектуры и направленности импортов во всех изменяемых слоях.
- **FR-003**: Аудит MUST проверить критические игровые сценарии на согласованность domain state, application execution, Pinia projections и UI результата.
- **FR-004**: Аудит MUST проверить маршруты, навигацию и состояния интерфейса для всех существующих игровых страниц на viewport `390×844`, `768×1024` и `1440×900`.
- **FR-005**: Аудит MUST подтвердить поведенческую эквивалентность SPA, Server и Hybrid для всех реализованных игровых сценариев: одинаковые допустимые действия, итоговое состояние и видимый результат; различия транспорта, хранения и промежуточной синхронизации допускаются. Нарушение этого контракта MUST классифицироваться как finding.
- **FR-006**: Каждый finding MUST иметь ID, severity, доказательство, шаги воспроизведения, ожидаемый и фактический результат, затронутый слой, рекомендацию и регрессионную проверку.
- **FR-007**: Исправления MUST выполняться только после полного `plan.md`, `tasks.md` и read-only consistency analysis.
- **FR-008**: Каждое исправление MUST сопровождаться релевантной автоматической или воспроизводимой ручной проверкой и повторным запуском затронутых quality gates.
- **FR-009**: Актуальные рабочие документы MUST синхронизироваться с подтверждёнными архитектурными или пользовательскими изменениями; архивные документы не переписываются.
- **FR-010**: Все подтверждённые findings уровней P0–P3 MUST быть исправлены до завершения work item; перенос подтверждённого finding за пределы work item не допускается.
- **FR-011**: При конфликте ожидаемое поведение MUST определяться по иерархии active spec → constitution/accepted ADR → актуальный GDD; код и тесты MUST рассматриваться как доказательство фактического поведения.

### Key Entities

- **Baseline**: зафиксированное начальное состояние репозитория и результаты обязательных проверок.
- **Finding**: подтверждённая проблема с доказательством, severity, воспроизведением, причиной и статусом.
- **Regression Check**: автоматическая или воспроизводимая ручная проверка, доказывающая отсутствие возврата конкретного дефекта.
- **Audit Matrix**: перечень проверяемых слоёв, сценариев, режимов исполнения и UI-маршрутов.
- **Mode Equivalence**: равенство допустимых игровых действий, итогового состояния и видимого результата между SPA, Server и Hybrid независимо от внутреннего механизма исполнения.

## Scope

**Включено:** связность слоёв, игровая логика, state synchronization, Nitro API, функциональная эквивалентность SPA/Server/Hybrid, реальные страницы и навигация, quality gates, тесты и актуальная рабочая документация.

**Исключено:** новые механики из backlog, отдельный Node.js backend Stage 8, платформенная интеграция, редизайн без подтверждённого дефекта, архивные документы как объект правки.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 100% существующих игровых маршрутов зарегистрированы в Audit Matrix отдельными строками для каждого обязательного viewport.
- **SC-002**: 100% подтверждённых findings P0–P3 устранены и имеют воспроизводимое доказательство исправления и назначенную регрессионную проверку; открытых или blocked findings при завершении нет.
- **SC-003**: 100% исправленных findings проходят исходный сценарий воспроизведения и связанную регрессионную проверку.
- **SC-004**: После каждого набора исправлений проходят все применимые обязательные quality gates без новых необоснованных нарушений.
- **SC-005**: Для каждого подтверждённого изменения поведения или архитектуры обновлён хотя бы один соответствующий рабочий документ.
- **SC-006**: 100% реализованных игровых сценариев имеют одинаковые допустимые действия, итоговое состояние и видимые результаты в SPA, Server и Hybrid; различия внутренних механизмов не влияют на результат.
- **SC-007**: 100% существующих игровых маршрутов проверены на viewport `390×844`, `768×1024` и `1440×900` без блокирующих layout-дефектов, console errors или тупиковых переходов.
