# Архитектурное решение: Адаптация паттерна Henderson

## Контекст

`game_life` использует ECS-ориентированную доменную модель с Nuxt + Pinia как UI-оркестрацию.
`henderson` использует тяжёлую store/service-архитектуру на Nuxt, спроектированную для API-управляемых e-commerce потоков.

Прямая миграция подхода `henderson` перенесла бы бизнес-правила в stores и размыла бы границу ECS.

## Решение

Принять гибридную архитектуру:

- Сохранить ECS как единственный источник доменной логики.
- Ввести явный прикладной слой между Pinia stores и ECS-системами.
- Разделить API прикладного слоя на команды (мутации) и запросы (только чтение).
- Заимствовать отдельные идеи `henderson` только для организации модулей и инфраструктурной гигиены.

## Границы слоёв

1. `src/stores/**`
   - владеет UI-состоянием и оркестрацией
   - может вызывать application фасад/use-cases
   - не должен напрямую импортировать ECS-системы
2. `src/domain/game-facade/**`
   - владеет прикладными use-cases и оркестрацией ECS-систем
   - может импортировать ECS-системы и world
3. `src/domain/ecs/**`
   - владеет доменным состоянием (компоненты), доменным поведением (системы) и world runtime

## Последствия

- Более чистое разделение ответственности и упрощение тестирования.
- Снижение риска разрастания stores по мере развития функционала.
- Постепенный путь миграции без ломающего переписывания.
