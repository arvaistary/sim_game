# Portable Agent Workflow

Переносимый разговорный рабочий процесс для AI-агента, который работает с кодом и документацией репозитория.

Рабочий процесс помогает пройти задачу от формулировки намерения до проверенного результата: собрать контекст, задать только необходимые вопросы, внести минимальное изменение, остановиться на ручной проверке, а затем провести аудит и финальную проверку кода.

> Пакет не содержит правил конкретного продукта или технологического стека. Контекст проекта подключается через адаптеры.

## Зачем он нужен

Пользователю не нужно вручную управлять фазами работы. Достаточно описать цель обычным языком. Агент сам:

- определяет текущую фазу и состояние репозитория;
- читает правила, документацию, код и тесты до начала реализации;
- задаёт сгруппированные вопросы только там, где без ответа может измениться результат;
- показывает сценарий ручной проверки и ждёт подтверждения пользователя;
- фиксирует найденные проблемы, повторяющиеся негативные паттерны и существенные решения;
- отделяет исходные ошибки проекта от новых регрессий и не заявляет о готовности без доказательств.

## Жизненный цикл задачи

Названия фаз являются стабильными идентификаторами рабочего процесса. Их смысл:

```text
Discovery → Clarification → Implementation → Manual QA
                                      ↘ обратная связь ↗
Manual QA → Audit → Code review → Close
```

| Фаза | Что делает агент | Результат перехода |
|---|---|---|
| **Discovery** | Изучает точку входа, адаптеры, правила, код, тесты и документацию; фиксирует исходное состояние и границы задачи. | Понятно, что менять и как проверить результат. |
| **Clarification** | Задаёт только существенные вопросы и фиксирует безопасные допущения. | Границы задачи и критерии приёмки согласованы. |
| **Implementation** | Вносит минимальное достаточное изменение, переиспользуя существующие решения. | Изменение собрано и проверено целевыми командами. |
| **Manual QA** | Даёт пользователю короткий сценарий ручной проверки с пограничными случаями. | Пользователь подтвердил результат или сообщил о баге. |
| **Audit** | Проверяет поведение, данные, безопасность, доступность, сопровождаемость и документацию. | Найденные проблемы записаны и имеют актуальный статус. |
| **Code review** | Проверяет финальный diff, границы задачи, архитектуру, вызывающие участки, обработку ошибок, тесты и лишнюю сложность. | Изменения понятны и готовы к закрытию. |
| **Close** | Подводит итог с доказательствами, известными ограничениями и оставшимися рисками. | Задача закрыта. |

Если пользователь сообщает о баге после Manual QA, агент возвращается к точечной реализации и снова проводит ручную проверку. Новая отдельная задача не создаётся, пока границы работы явно не расширены.

## Память и восстановление задачи

Workflow не полагается на память модели или на скрытое состояние инструмента. Для текущей задачи используется видимый Markdown-файл состояния, путь к которому задаёт проектный адаптер. Его формат описан в [`templates/task-state.md`](templates/task-state.md).

Файл состояния хранит только рабочий checkpoint:

- идентификатор и цель задачи;
- текущую фазу и критерии приёмки;
- границы, решения и допущения;
- изменённые файлы и выполненные проверки;
- известные ошибки, режим проверки и следующее действие;
- заметки, необходимые для передачи работы другому агенту.

Стабильные правила проекта хранятся в адаптерах, решения — в журнале решений, findings и recurring patterns — в своих журналах, а закрытые задачи — в каталоге истории. Эти записи не смешиваются и не заменяют друг друга.

Checkpoint обновляется на границах фаз и перед остановкой. Если агент продолжает работу после сжатия контекста или аварийного завершения, он сначала читает активное состояние, проверяет файлы и Git, повторяет необходимые проверки и только затем продолжает с `Next action`. Старый вывод команд без повторной проверки не считается доказательством.

Если активного checkpoint нет, агент создаёт новый с уникальным `TASK-ID`. При `Status: Active` или `Status: Blocked` он возобновляет существующую задачу. При `Status: Closed` сначала проверяет архив `TASK-YYYYMMDD-NNN.md`, затем создаёт новый идентификатор; закрытая запись не перезаписывается. Неизвестный или повреждённый статус считается блокером.

Checkpoint обновляется перед и после Audit, code review и Close. Закрытая запись сохраняется в каталоге истории до замены активного файла.

Такая память намеренно простая: она видима в репозитории, переносима между агентами и не требует отдельной базы данных или расширения Codex. Не записывайте в неё секреты.

## Как устроен пакет

Пакет разделён на слои. Это позволяет переносить рабочий процесс между проектами, заменяя только контекстные части.

| Каталог или файл | Назначение |
|---|---|
| [`layers/core.md`](layers/core.md) | Технологически независимый жизненный цикл, контракт доказательств и границы безопасности. |
| [`layers/host-codex.md`](layers/host-codex.md) | Поведение Codex и правила разговорного взаимодействия. |
| [`layers/environment-windows.md`](layers/environment-windows.md) | Политика работы в Windows: сначала системная оболочка, затем явный резервный вариант через Git Bash. |
| [`layers/technology.template.md`](layers/technology.template.md) | Шаблон адаптера языка, среды выполнения, фреймворка, архитектуры и команд проверки. |
| [`layers/project.template.md`](layers/project.template.md) | Шаблон адаптера продукта, репозитория, источников требований и локальных журналов. |
| [`skills/`](skills/) | Канонические навыки для отдельных этапов рабочего процесса. |
| [`checklists/`](checklists/) | Чеклисты аудита и финальной проверки кода. |
| [`standards/`](standards/) | Переиспользуемые инженерные правила. |
| [`templates/`](templates/) | Форматы записей журналов для найденных проблем, повторяющихся паттернов и решений. |
| [`templates/task-state.md`](templates/task-state.md) | Формат активного checkpoint и передачи задачи. |
| [`scripts/validate.py`](scripts/validate.py) | Структурная проверка пакета без внешних зависимостей. |

Ядро рабочего процесса отвечает за процесс. Адаптеры добавляют контекст и команды проверки, но не должны молча менять жизненный цикл или границы подтверждений.

## Навыки

Канонические навыки имеют стабильные имена, чтобы интеграции с инструментами могли ссылаться на них независимо от проекта:

- [`agent-task-flow`](skills/task-flow/SKILL.md) — основной разговорный рабочий процесс;
- [`agent-audit`](skills/audit/SKILL.md) — аудит после ручной проверки;
- [`agent-code-review`](skills/code-review/SKILL.md) — финальная проверка изменений;
- [`agent-windows-shell`](skills/windows-shell/SKILL.md) — работа с оболочкой Windows и резервным запуском.

В целевом репозитории можно добавить тонкие локальные оболочки в `.agents/skills/`. Такая оболочка только подключает канонический навык и не должна дублировать его правила.

## Интеграция в проект

### 1. Подключите пакет

Клонируйте репозиторий в директорию, которую будет видеть точка входа проекта:

```bash
git clone https://github.com/arvaistary/ai-workflow.git agent-workflow
```

Пакет также можно подключить другим способом, если это соответствует правилам проекта.

### 2. Создайте адаптеры

Скопируйте шаблоны и заполните их контекстом целевого проекта:

- технологический адаптер: язык, среда выполнения, фреймворк, архитектура и команды проверки;
- проектный адаптер: источники требований, локальные правила, журналы и границы задачи.

Адаптеры могут находиться, например, в `doc/agent-workflow/`. Их задача — дать контекст, а не переопределить жизненный цикл или границы подтверждений.

В проектном адаптере укажите отдельные пути для активного состояния задачи и истории закрытых задач. Создайте активный checkpoint на основе [`templates/task-state.md`](templates/task-state.md).

### 3. Подключите точку входа

Добавьте или обновите `AGENTS.md` на основе [`layers/AGENTS.template.md`](layers/AGENTS.template.md). Точка входа должна указать:

- этот пакет;
- выбранный технологический адаптер;
- выбранный проектный адаптер;
- канонические навыки или тонкие локальные оболочки.

Не помещайте продуктовые правила в `layers/core.md` или канонические навыки.

### 4. Проверьте интеграцию

Из корня целевого репозитория:

```bash
python agent-workflow/scripts/validate.py
```

Из корня самого пакета:

```bash
python scripts/validate.py .
```

После этого запустите релевантные проверки технологического адаптера и выполните ручную проверку интеграции.

## Границы безопасности

Workflow намеренно не создаёт автоматически:

- ветки, worktree, commit, merge и pull request;
- состояние планирования другого инструмента;
- развёртывания, сообщения и внешние записи;
- изменения за пределами разрешённых границ задачи.

Перед разрушительными или необратимыми действиями, доступом к учётным данным, работой с внешними системами, изменением публичных контрактов, существенным изменением архитектуры или введением новой политики агент останавливается и запрашивает решение.

Режим «Полный доступ» означает доступ к разрешённому рабочему пространству, но не означает права Windows Administrator или разрешение воздействовать на внешние системы.

## Резервный запуск в Windows

В Windows сначала используется системная оболочка, указанная окружением. При ошибке запуска `CreateProcess`, `helper` или эквивалентной ошибке агент прекращает бесконечные повторы и проверяет явный Git Bash:

```powershell
$gitBash = 'C:\Program Files\Git\bin\bash.exe'
& $gitBash -lc '<same safe command>'
```

Нельзя использовать просто `bash.exe`, `C:\Windows\System32\bash.exe`, псевдонимы WindowsApps или WSL как резервный вариант Git Bash. Режим проверки фиксируется одним из стабильных идентификаторов: `native-shell-ok`, `fallback-required`, `fallback-ok`, `elevated-fallback`, `fallback-failed` или `blocker`.

Подробные правила находятся в [`layers/environment-windows.md`](layers/environment-windows.md).

## Принципы изменений

При изменении пакета:

1. сохраняйте ядро технологически независимым;
2. добавляйте проектные детали в адаптеры, а не в ядро или навыки;
3. не дублируйте правила между навыком, чеклистом и слоем без необходимости;
4. сохраняйте стабильные имена навыков, пути и статусы журналов;
5. запускайте `validate.py` и релевантные проверки изменённых файлов;
6. описывайте в проверке кода, как изменение сохраняет переносимость.
