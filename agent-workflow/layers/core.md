# Ядро workflow

## Жизненный цикл

```text
Discovery → Clarification → Implementation → Manual QA
                                      ↘ feedback ↗
Manual QA → Audit → Code review → Close
```

Пользователь выбирает направление продукта. Агент управляет обычными переходами между фазами и сообщает текущую фазу на языке пользователя.

### Discovery — исследование

- Прочитайте host entrypoint, подходящие проектный и технологический адаптеры, релевантные правила, код, тесты и документацию.
- Зафиксируйте baseline, scope, non-goals, риски, переиспользуемые паттерны и одно рекомендуемое следующее действие.
- Не задавайте вопросы, на которые уже может ответить содержимое репозитория.

### Clarification — уточнение

- Задавайте сгруппированные вопросы только если ответ меняет scope, поведение, совместимость, риск или критерии приёмки.
- Явно сообщайте безопасные допущения.
- Фиксируйте существенные решения в журнале решений проекта.

### Implementation — реализация

- Вносите минимальное достаточное изменение и сохраняйте несвязанную работу.
- Перед добавлением абстракций или зависимостей ищите существующие паттерны.
- Для изменений детерминированного поведения по возможности сначала добавляйте regression coverage.
- Для ошибок: воспроизведите, изолируйте, проследите общую причину, исправьте её и повторите целевые проверки.

### Manual QA — ручная проверка

- Предоставьте короткий сценарий ручной проверки с ожидаемыми результатами и edge cases.
- Остановитесь и дождитесь ручной проверки пользователя.
- Считайте найденные пользователем дефекты частью текущей задачи, если пользователь явно не расширяет scope.

### Audit — аудит

- После Manual QA запускайте подходящий audit checklist.
- Фиксируйте findings до изменения кода.
- Проверяйте поведение, целостность данных, безопасность, accessibility, сопровождаемость, документацию и риск регрессий.
- Выделяйте recurring patterns только если доказательства подтверждают минимум две связанные находки или одну серьёзную системную находку.

### Code review

- Проверяйте финальный diff относительно критериев приёмки и наблюдаемого поведения.
- Проверяйте scope, callers, переходы состояния, error paths, сложность, dead code, дублирование, тесты и документацию.
- Выполняйте только безопасную cleanup-работу в рамках scope, затем повторяйте затронутые проверки.

### Close — завершение

Завершайте задачу только когда требуемое поведение работает, релевантные проверки проходят или известные baseline failures задокументированы, feedback ручной проверки обработан, findings имеют статусы, а финальный diff понятен. Перед закрытием сохраните checkpoint в истории под уникальным именем `TASK-YYYYMMDD-NNN.md`.

## Автоматические переходы

- Новая задача → Discovery.
- Получены необходимые ответы → Implementation.
- Реализация завершена → Manual QA.
- Пользователь сообщил о баге → точечная реализация → Manual QA.
- Пользователь подтвердил Manual QA → Audit → Code review → Close.
- Изменился scope или появилась новая policy → остановитесь и запросите решение.

## Память и состояние задачи

Workflow не зависит от скрытой памяти модели. Долговременный контекст собирается из видимых источников:

- стабильные правила и адаптеры проекта;
- журнал решений;
- журналы findings и recurring patterns;
- сохранённые файлы и текущее состояние Git;
- активный файл состояния задачи и архив закрытых задач.

Проектный адаптер обязан указать путь к активному состоянию задачи и каталог истории. Формат активного состояния задан в [`templates/task-state.md`](../templates/task-state.md). Файл состояния — источник истины для текущих `Phase`, цели, критериев приёмки, проверок, блокеров и `Next action`; он не заменяет журналы решений, findings или recurring patterns.

Создайте или обновите checkpoint:

- при старте задачи;
- после Discovery и Clarification;
- после каждого существенного блока Implementation;
- перед остановкой на Manual QA;
- после каждого бага, сообщённого пользователем;
- перед паузой, передачей работы другому агенту или рискованным действием;
- перед началом Audit, Code review и Close;
- после Audit и Code review с результатом фазы и следующим действием.

Checkpoint не должен содержать секреты. После закрытия задачи установите `Status: Closed`, `Phase: Close` и сохраните запись в каталоге истории; историю не удаляйте.

### Начало и архивирование задач

При старте новой задачи:

- если активного файла нет, создайте новый checkpoint с уникальным `TASK-ID`;
- если `Status: Active` или `Status: Blocked`, возобновите существующую задачу;
- если `Status: Closed`, сначала проверьте наличие записи с именем `TASK-YYYYMMDD-NNN.md` в каталоге истории, указанном в проектном адаптере, затем создайте новый уникальный `TASK-ID` и только после этого замените активный файл;
- если состояние отсутствует, повреждено или содержит неизвестный статус, остановитесь и сообщите о блокере.

Перед заменой закрытого активного файла сохраните его полную копию в каталоге истории из проектного адаптера. Не используйте повторно существующий `TASK-ID` и не перезаписывайте архивную запись.

### Восстановление после прерывания

Если активный checkpoint имеет `Status: Active` или `Status: Blocked`, сначала возобновите эту задачу, а не создавайте параллельную. Прочитайте файл состояния, затем проверьте `git status`, diff и состояние файлов. Повторно выполните необходимые целевые проверки: старый вывод команд нельзя считать актуальным без перепроверки. После этого продолжайте с указанного `Next action` или исправьте его, если фактическое состояние изменилось.

После Audit и code review обновляйте `Phase`, результаты проверки, findings, ограничения и `Next action` до возможной остановки. Так следующий агент сможет продолжить с актуальной границы, даже если остановка произошла после Manual QA.

При сжатии контекста или аварийной остановке файл состояния является контрактом передачи работы следующему агенту. В нём должны быть текущая фаза, сохранённые изменения, выполненные проверки, известные ограничения, требуемые подтверждения и следующее действие.

## Границы безопасности

Останавливайтесь перед destructive или необратимыми действиями, внешними side effects, работой с credentials, изменением public contract, существенно отличающейся архитектурой или новой restrictive policy.

Не создавайте workflow-артефакты, принадлежащие другому host или инструменту, если пользователь явно не запросил этот workflow.

## Контракт доказательств

На границах фаз сообщайте:

```text
Фаза: <phase>
Состояние: <baseline or result>
Следующее действие: <recommendation>
Нужно от пользователя: <questions, manual QA, or none>
```

Никогда не заявляйте о завершении, если обязательная проверка недоступна, не проходит или не подтверждена.
